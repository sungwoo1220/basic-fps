# 런처에서 DX11 게임 설치·업데이트·실행 (라이엇 방식)

## 의도와 이유
사용자는 라이엇처럼 **런처를 한 번만 설치**하고, 게임이 업데이트돼도 **런처를 열면 알아서 최신으로 받은 뒤 플레이 버튼 하나로 실행**되길 원한다. 지금은 DX11 시험판(`BasicFPS-DX11.exe`)을 ZIP으로 직접 받아 풀어야 하고, 런처는 DX11을 모른다.

## 목표
1. 런처를 켜면 자동으로 최신 DX11 버전을 확인하고, 있으면 바뀐 파일만 받아 설치한다.
2. 업데이트가 끝나면 큰 **플레이 버튼**이 켜지고, 누르면 `BasicFPS-DX11.exe`가 실행된다.
3. 화면은 DX11 중심으로 단순해진다. 기존 브라우저 게임과 언리얼은 "고급"에 접어 둔다.
4. 업데이트가 실패하면 이전 설치본을 그대로 쓴다. 인터넷이 없어도 설치돼 있으면 플레이할 수 있다.
5. 마우스 감도는 업데이트해도 유지된다(이미 `%LOCALAPPDATA%/BasicFPS-DX11/sensitivity.txt`에 저장됨). 닉네임은 지금도 저장하지 않으므로 이번 작업에서 바꾸지 않는다.

## 비목표
- 런처 자체의 자동 업데이트(서명 없는 설치 파일을 자동 교체하는 위험). 이번에 새 설치 파일을 **한 번** 설치한다.
- 코드 서명, 바이너리 차분(delta) 압축, Windows 외 OS.
- 기존 브라우저 게임·언리얼 경로의 동작 변경.

## 안티 목표 (이렇게 되면 기능이 돼도 실패)
- 게임이 실행 중인데 파일을 교체한다.
- 반쪽만 올라간 릴리스를 런처가 받는다.
- 업데이트 때문에 사용자 설정이 사라진다.
- 기존 `npm test`(언리얼 업데이트 시험 포함)가 깨진다.

## 제약
- 신뢰 모델은 지금과 같다: GitHub HTTPS, SHA-256 검증, 목록 서명 없음. 업데이트 주소는 `github.com/sungwoo1220/basic-fps/releases/download/<태그>/…`로 고정한다.
- 릴리스 하나당 첨부 파일 1000개·파일당 2GB 한도. 조각 크기는 8MB(기존 `MAX_CHUNK`).
- DX11 시험판은 `--prerelease --latest=false`로 게시하므로 런처 설치 파일·게임 패치(최신 릴리스)와 섞이지 않는다. 이 분리를 유지한다.
- `AGENTS.md`의 "런처는 DX11 시험판을 받지 않는다" 결정을 이번에 뒤집으므로 문서를 고친다.

## 접근 방법
| | 방법 | 장단점 |
|---|---|---|
| **A (선택)** | `native-update.cjs`를 프로필(언리얼/DX11)로 일반화하고, DX11 릴리스에 `dx11-update.json`(파일별 해시·조각 주소)과 조각 파일을 함께 올린다 | 검증·복구·무결성 코드를 그대로 재사용. 바뀐 파일만 받는다. 릴리스마다 모든 조각을 다시 올려 저장 용량이 늘어 오래된 릴리스를 정리해야 한다 |
| B | ZIP 전체를 받아 통째로 교체 | 가장 단순하지만 `node.exe`(약 90MB)가 있어서 매번 전체를 받는다. 해시 검증·복구는 새로 짜야 한다 |
| C | `electron-updater` 도입 | 런처 자체 업데이트까지 풀리지만 서명 없는 설치 파일 자동 교체 위험이 크고 게임 파일 증분 방식과 별개다 |

사용자는 화면 방향(DX11 메인, 나머지는 고급)을 골랐고, 내부 방식은 위임했다. **A로 간다.**

## 결정한 구조 (제 판단이며 사용자가 직접 정한 것이 아니다)
1. **업데이트 목록**: `scripts/publish-dx11.cjs`가 조립된 폴더(`BasicFPS-DX11.exe`, `README.md`, `room/…`)를 읽어 `scripts/publish-unreal.cjs`와 같은 방식으로 8MB 조각·해시를 만들고 `dx11-update.json`을 쓴다. 태그는 `dx11-test-N-M`, `kind:'dx11'`, `platform:'win64'`, 실행 파일은 `BasicFPS-DX11.exe`.
2. **클라이언트**: `NativeClient`가 프로필(`kind`, 태그 정규식, 목록 이름, 폴더 접두어와 `folderOK`, 실행 파일 검사식, 안내 문구)을 받도록 바꾼다. `validateManifest(m, profile=UNREAL)`처럼 **기본값을 언리얼로 두어** `pack(source,output,tag)`, `new NativeClient({root,emit,fetch})`, 기존 호출과 언리얼 문구(시험이 정규식으로 검사: 준비 완료, 손상, 달라졌어요, 아직 다운로드할, 이전 시험판으로 복구)는 한 글자도 바꾸지 않는다. `latest()`의 폴더 접두어 길이 계산(`ue-test-`)도 프로필에서 가져오고, 릴리스 목록은 `per_page=100`으로 읽어 `build-*` 릴리스에 가려지지 않게 한다. DX11 문구에는 "언리얼"을 쓰지 않는다. DX11 인스턴스는 `userData/dx11`에 설치하고 새 버전 하나와 이전 버전 하나만 남긴다. 프로필을 새 파일로 빼면 `package.json`의 `build.files`에 반드시 추가한다.
3. **게시**
   - Windows 빌드 작업이 조립된 폴더에서 ZIP과 조각·`dx11-update.json`을 **같은 바이트로** 만들어 아티팩트 하나로 올린다. 게시 작업은 그 아티팩트만 받아 올리므로 checkout이 필요 없다.
   - 게시 작업은 릴리스를 **초안으로** 만들고, 조각을 20개씩 올리고, 목록을 맨 마지막에 올린 뒤 초안을 푼다(`--prerelease --latest=false`). 반쪽 릴리스를 막는 순서다. ZIP 이름 `BasicFPS-DX11-Win64.zip`과 `SHA256SUMS.txt`는 그대로 올린다(다운로드 페이지가 이 이름을 쓴다).
   - 새 스크립트 `scripts/publish-dx11.cjs`(묶기)와 `scripts/upload-dx11-release.cjs`(올리기)를 만든다. 언리얼용 `publish-unreal.cjs`·`upload-unreal-release.cjs`는 건드리지 않고 조각 나누기 로직만 공유한다. 목록 `version`은 `0.2.<run*100+attempt>`다.
   - 고유 조각이 990개를 넘으면 묶기를 실패시킨다.
   - 정리: 태그 번호(run, attempt) 기준 최근 5개를 남기고 나머지 `dx11-test-*` 릴리스·태그와 남은 초안을 지운다(`gh release delete --cleanup-tag`).
   - `dx11.yml`의 `paths`(push·pull_request 둘 다)에 `scripts/publish-dx11.cjs`, `scripts/upload-dx11-release.cjs`, `native-update.cjs`를 넣는다.
4. **런처 동작**
   - 시작하면 DX11 확인·설치를 **먼저** 하고, 끝난 뒤 기존 브라우저 게임 업데이트를 한다(둘 다 같은 `busy` 잠금을 쓰기 때문).
   - 실패해도 설치본이 있으면 플레이할 수 있다. 플레이는 설치 파일 해시를 모두 확인한 뒤(`node.exe` 때문에 몇 초 걸리므로 "파일 확인 중" 문구를 보여 준다) `BasicFPS-DX11.exe`를 인수 없이 실행한다.
   - 게임 실행 중에는 업데이트를 막고, 시작 직후 실패하면 DX11용 인스턴스의 복구 로직으로 이전 버전을 되돌린다.
   - `main.cjs`의 `play`/`start`는 지금 브라우저 게임이 설치돼 있어야 하고, 모르는 client 값을 `browser`로 바꾸며, 언리얼 인수(`-ServerUrl` 등)를 붙인다. client 값에 `dx11`을 추가하고 이 가드·인수·복구 대상을 client별로 나눈다.
   - **창을 닫을 때(사용자 결정)**: 지금처럼 런처를 닫으면 게임도 함께 종료된다. 동작은 바꾸지 않는다.
5. **화면**: 큰 플레이 버튼, 설치 버전, 상태·진행률. "고급" 접이식 영역에 지금의 게임 선택·방 열기·서버 주소·수동 업데이트 버튼을 그대로 둔다.
6. **시험**: `game/tests/dx11-update.cjs`(묶기→설치→바뀐 파일만 받기→손상 거부→복구), `game/tests/native-launcher.cjs`에 DX11 플레이 항목 추가, `package.json` `test` 스크립트와 `AGENTS.md`·`README.md` 갱신.

## 검토에서 확인한 것
- 파일 경로 규칙(`safePath`), 첨부 개수(약 100개 미만), 2GB 한도, `electron-builder`의 `files` 목록은 문제없다.
- 조립 후 게임이 패키지 폴더에 파일을 쓰지 않아 플레이 때 해시 검사가 깨지지 않는다(방 로그는 `%TEMP%`, 설정은 `%LOCALAPPDATA%`).
- 방 서버는 게임이 죽으면 함께 죽도록 묶여 있어 고아 `node.exe`가 남지 않는다.

## 빌더에게 맡기는 것
진행률 막대 모양과 문구, 파일 이름·폴더 이름 세부, 오래된 릴리스 삭제 명령의 정확한 형태, 한국어 안내 문구.

## 알려진 한계
- 릴리스마다 `node.exe` 조각을 다시 올려 릴리스당 약 100MB가 늘어난다(5개만 유지).
- 새 런처 설치 파일을 사용자가 한 번 설치해야 한다. 노트북 실물 GPU·독점 전체화면 확인은 여전히 사용자 몫이다.
